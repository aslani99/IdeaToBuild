# ARCHITECTURE DECISION RECORDS (ADR)

هر تصمیم معماری مهم اینجا با شناسه، تاریخ، مشکل، گزینه‌های بررسی‌شده، تصمیم نهایی و پیامدها ثبت می‌شود.

---

## AD-001 — Frontend Stack
**تاریخ:** 2026-08-23
**مشکل:** نیاز به یک فریم‌ورک frontend که بین دسکتاپ (Tauri)، وب و در آینده موبایل قابل استفاده‌ی مجدد باشد.
**گزینه‌ها:** React، Vue، Svelte
**تصمیم:** React + TypeScript + Vite
**دلیل:** بلوغ اکوسیستم، سازگاری کامل با Tauri 2، پشتیبانی قوی از TypeScript strict، جامعه‌ی بزرگ برای کتابخانه‌های i18n/RTL.
**پیامدها:** تمام منطق دامنه/اپلیکیشن باید مستقل از React نوشته شود تا برای وب/موبایل هم قابل استفاده باشد.

## AD-002 — Desktop Shell
**تاریخ:** 2026-08-23
**مشکل:** نیاز به یک shell دسکتاپ سبک، امن و بومی برای ویندوز (و بعداً macOS/Linux).
**گزینه‌ها:** Electron، Tauri 2، Native (WinUI3/C#)
**تصمیم:** Tauri 2
**دلیل:** حجم باینری کوچک‌تر، مدل امنیتی مبتنی بر capabilities با least-privilege، Rust فقط برای بخش‌های حساس/بومی، امکان اشتراک منطق React با وب آینده.
**پیامدها:** Rust فقط در `src-tauri` برای فایل‌سیستم، دیالوگ‌های بومی و عملیات حساس امنیتی استفاده می‌شود؛ منطق دامنه در Rust تکرار نمی‌شود.

## AD-003 — Backend Platform
**تاریخ:** 2026-08-23
**مشکل:** نیاز به احراز هویت، دیتابیس رابطه‌ای، Row Level Security، و توابع سمت سرور بدون ساخت زیرساخت از صفر.
**گزینه‌ها:** Firebase، AWS خام، Supabase
**تصمیم:** Supabase (PostgreSQL + Auth + RLS + Realtime + Edge Functions)
**دلیل:** RLS بومی Postgres برای امنیت در سطح ردیف، سازگاری با معماری خودمالکیتی داده (self-hostable در آینده)، سرعت توسعه.
**پیامدها:** تمام دسترسی به داده باید از پشت RLS عبور کند؛ کلید service-role هرگز در کلاینت قرار نمی‌گیرد.

## AD-004 — Object Storage
**تاریخ:** 2026-08-23
**مشکل:** ذخیره‌ی فایل‌های حجیم کاربر بدون سنگین کردن دیتابیس اصلی.
**گزینه‌ها:** ذخیره در Postgres (BLOB)، AWS S3، Cloudflare R2
**تصمیم:** Cloudflare R2 برای آبجکت‌ها، Postgres فقط برای متادیتا
**دلیل:** هزینه‌ی پایین‌تر (بدون egress fee)، سازگاری با S3 API، جداسازی تمیز متادیتا از داده‌ی باینری.
**پیامدها:** یک لایه‌ی انتزاعی storage (`infrastructure/storage`) ساخته می‌شود تا در آینده تعویض provider ممکن باشد.

## AD-005 — No AI Inside the Product
**تاریخ:** 2026-08-23
**مشکل:** جلوگیری از وابستگی محصول نهایی به سرویس‌های AI خارجی و ارسال داده‌ی کاربر به مدل‌های زبانی.
**تصمیم:** محصول تولیدی هیچ قابلیت AI/LLM ندارد. AI فقط ابزار توسعه است.
**دلیل:** حریم خصوصی کاربر، کنترل کامل روی رفتار محصول، عدم وابستگی به هزینه/در دسترس بودن API خارجی.
**پیامدها:** هیچ فراخوانی به API هوش مصنوعی از کد تولیدی مجاز نیست؛ این قانون فقط با تأیید صریح مالک پروژه قابل تغییر است.

## AD-008 — Explicit Workspace Membership Table
**تاریخ:** 2026-08-25
**مشکل:** مدل چندنفره‌ی Workspace (docs/PRODUCT_SPEC.md) در آینده (Phase 17+) نیاز به بیش از یک عضو در هر Workspace دارد؛ تکیه‌ی صرف بر ستون `owner_id` نیاز به migration اسکیمای بزرگ در آن فاز دارد.
**تصمیم:** از همین Phase 2 (نسخه‌ی تک‌کاربره) یک جدول جداگانه‌ی `workspace_members` با ستون `role` (`owner`/`admin`/`member`/`viewer`) ساخته شد؛ حتی صاحب یک Workspace شخصی هم یک ردیف عضویت با `role='owner'` دارد (تضمین‌شده توسط تابع `create_workspace_with_owner`).
**دلیل:** افزودن عضو جدید در آینده فقط نیاز به `insert` یک ردیف دارد، نه تغییر اسکیما؛ همچنین RLS Policy‌ها می‌توانند از روز اول بر پایه‌ی عضویت/نقش نوشته شوند، نه `owner_id ==`، که تغییرشان در آینده هم‌ارز بازنویسی کامل Policy است.
**پیامدها:** هر عملیات create workspace باید هم‌زمان یک ردیف `workspaces` و یک ردیف `workspace_members` بسازد — برای جلوگیری از race condition/Workspace بدون مالک، این کار در یک تابع Postgres با `security definer` (`create_workspace_with_owner`) انجام می‌شود، نه در کد کلاینت با دو `insert` جدا. تمام کوئری‌های RLS روی `workspaces`/`categories`/`tags` از طریق `exists (select 1 from workspace_members ...)` عبور می‌کنند.

## AD-009 — Date-Driven Navigation ("Entry Date" as the app's home)
**تاریخ:** 2026-08-26
**مشکل:** مالک پروژه می‌خواهد کل تجربه‌ی اپ حول یک «تاریخ فعال» بچرخد: هر رکورد (فعلاً Idea، بعداً Note/File) به یک روز مشخص تعلق دارد؛ باز کردن اپ یعنی دیدن رکوردهای امروز؛ انتخاب یک تاریخ دیگر از تقویم یعنی رفتن به اطلاعات همان روز. کاربر باید بتواند تاریخ نمایش را بین شمسی/میلادی/قمری عوض کند بدون خراب‌شدن داده.
**تصمیم:**
1. یک ستون جدید `entry_date` (نوع `date`، بدون زمان/منطقه‌ی زمانی) به `ideas` اضافه شد — همیشه به فرمت میلادی خنثی ذخیره می‌شود؛ فقط نمایش آن بر اساس تقویم انتخابی کاربر (`Intl.DateTimeFormat` با `-u-ca-persian`/`-u-ca-islamic`) تبدیل می‌شود.
2. یک «تاریخ فعال» سراسری (`ActiveDateContext`) در بالاترین سطح اپ (`App.tsx`) قرار گرفت؛ هر پنل داده‌محور (فعلاً `IdeasPanel`) از همین context می‌خواند، نه یک state محلی جدا.
3. `entry_date` مستقیماً قابل ویرایش نیست — `update()` صراحتاً این فیلد را نمی‌پذیرد. تنها دو مسیر تغییر: `moveToDate` (جابه‌جایی خودِ رکورد به روز دیگر) و `copyToDate` (کپی رکورد به روز دیگر، اصل دست‌نخورده). هر دو به‌صورت RPC های Postgres (`move_idea_to_date`, `copy_idea_to_date`) پیاده شدند، نه `update`/`insert` مستقیم از کلاینت — تا در آینده اگر تاریخچه/audit لازم شد، یک نقطه‌ی واحد برایش وجود داشته باشد.
**دلیل:** جدا نگه‌داشتن «روزی که رکورد بهش تعلق دارد» از `created_at`/`updated_at` (که صرفاً زمان فنی رخداد است) امکان می‌دهد کاربر بدون خراب‌کردن تاریخچه‌ی واقعی، محتوا را بین روزها جابه‌جا/کپی کند. ذخیره‌ی همیشه-میلادی از مشکلات گرد کردن/محاسبه‌ی نادرست هنگام تبدیل بین تقویم‌ها جلوگیری می‌کند؛ فقط لایه‌ی نمایش درگیر تبدیل تقویم می‌شود.
**پیامدها:**
- تمام موجودیت‌های آینده که Section بعدی نیاز به این مدل دارند (Notes، Files) باید همین الگو (`entry_date` + RPC move/copy) را تکرار کنند، نه یک الگوی متفاوت هر بار.
- انتخابگر تقویم فعلی (`DateNavigator`) از `<input type="date">` بومی مرورگر استفاده می‌کند (که همیشه میلادی نمایش داده می‌شود) به‌همراه یک برچسب متنی که در تقویم انتخابی کاربر فرمت می‌شود. ساخت یک widget کامل شبکه‌ی تقویم شمسی/قمری (مثل ماه‌شمارهای گرافیکی واقعی) هنوز کار نشده — این تصمیم آگاهانه‌ی MVP است، نه فراموشی؛ پیگیری در docs/ROADMAP.md.
- انتخاب تقویم نمایشی (شمسی/میلادی/قمری) فعلاً فقط در state موقت React (`DateNavigator`) نگه داشته می‌شود، نه در تنظیمات دائمی کاربر — ذخیره‌سازی دائمی این ترجیح، کار آینده است.

## AD-010 — Local-First Storage + Background Sync (Ideas), Guest Save-Gating
**تاریخ:** 2026-08-26
**مشکل:** مالک پروژه سه تا نیازمندی مرتبط اعلام کرد: (۱) مهمان باید بتونه کل اپ رو آزادانه ببینه، فقط لحظه‌ای که می‌خواد چیزی ذخیره کنه کادر ثبت‌نام/ورود ظاهر بشه؛ (۲) بعد از ثبت‌نام، سشن کاربر نگه داشته بشه (نیازی به ورود دوباره در دفعات بعد نباشه)؛ (۳) داده‌ها اول رو خود دستگاه (رمزنگاری‌شده، غیرقابل‌دسترس از فایل‌منیجر) ذخیره بشن، و با تأخیر کوتاه در صورت اتصال اینترنت خودکار با Supabase همگام بشن؛ اگه آفلاین بود، تا اتصال بعدی صف بمونن.
**تصمیم:**
1. `useAuth` به `AuthContext` تبدیل شد (رفع باگ جداگانه‌ی state) و توابع `requireAuth()`/`AuthRequiredModal` اضافه شد: هر عمل ذخیره‌سازی (ساخت Workspace/Category/Tag/Idea) قبل از اجرا `requireAuth()` رو صدا می‌زنه؛ اگه کاربر مهمان باشه، به‌جای اجرای عملیات، مودال ثبت‌نام/ورود باز میشه.
2. Session persistence: در `AuthProvider`، هنگام mount اپ، `restoreSession()` (متد جدید `IAuthRepository`) چک می‌کنه آیا سشن Supabase از قبل معتبره؛ اگه بله، کاربر مستقیم authenticated لود میشه، نه guest.
3. برای Idea (به‌عنوان اولین موجودیت)، یک لایه‌ی ذخیره‌سازی محلی رمزنگاری‌شده ساخته شد: `src-tauri/src/local_store.rs` با یک دیتابیس SQLite ساده (**نه SQLCipher** — به دلیل پیچیدگی build با OpenSSL روی ویندوز MSVC) که فیلدهای حساس هر رکورد با AES-256-GCM رمزنگاری میشن قبل از ذخیره؛ کلید رمزنگاری در Windows Credential Manager (از طریق crate با نام `keyring`) نگه‌داری میشه، نه در یک فایل ساده.
4. `LocalFirstIdeaRepository` (پیاده‌سازی جدید `IIdeaRepository`) جایگزین `SupabaseIdeaRepository` در `useIdeas` شد — همه‌ی خواندن/نوشتن اول محلی انجام میشه؛ `id` رکورد همون لحظه‌ی محلی (با `crypto.randomUUID()`) ساخته میشه و همون‌طور برای ردیف Supabase هم استفاده میشه (نه `gen_random_uuid()` سمت سرور) تا هیچ‌وقت مشکل نگاشت شناسه‌ی محلی↔ابری پیش نیاد.
5. یک `SyncEngine` (لایه‌ی application) با یک اینترفیس باریک `IIdeaSyncTarget` (که `SupabaseIdeaRepository` هم پیاده‌سازیش می‌کنه) ساخته شد: صف تغییرات محلی رو (تابع Rust `get_pending`) می‌خونه، هر رکورد رو با `.upsert()` مستقیم به Supabase push می‌کنه (نه از طریق RPCهای `move_idea_to_date`/`copy_idea_to_date` که برای مسیر آنلاین مستقیم بودن — اینجا دستگاه محلی منبع حقیقته، نه دیتابیس ابری)، و بعد از موفقیت `mark_synced` می‌زنه.
**دلیل:** رمزنگاری سطح‌فیلد با AES-256-GCM + کلید در credential store سیستم‌عامل، امنیت واقعی (نه فقط پنهان‌کاری تو یه پوشه) رو بدون نیاز به کامپایل پیچیده‌ی SQLCipher/OpenSSL فراهم می‌کنه. یکی‌بودن id محلی/ابری، منطق sync رو خیلی ساده‌تر می‌کنه (فقط `upsert`، نه نگاشت شناسه). صف sync بر اساس «آخرین وضعیت هر رکورد» (نه تاریخچه‌ی عملیات) طراحی شده تا با از دست رفتن ترتیب یا تلاش‌های ناقص، هم‌گرا بمونه.
**پیامدها:**
- این الگو فقط برای Idea پیاده شده؛ Workspace/Category/Tag هنوز مستقیم آنلاین (فقط Supabase) هستن — گسترش همین الگو به اون‌ها، کار آینده‌ست، نه فراموشی.
- soft-delete محلی (فلگ `deleted`، نه timestamp) موقع sync به `deleted_at` واقعی تبدیل میشه؛ ولی اگه رکورد قبل از اولین sync موفق حذف بشه، صف فقط آخرین وضعیت (حذف‌شده) رو نگه می‌داره — این عمداً همینه (طبق طراحی صف).
- **محدودیت امنیتی صادقانه** (طبق قانون «هرگز ادعای امنیت ۱۰۰٪ نکن»، بخش ۱۹ سند اصلی): این رمزنگاری در برابر باز کردن ساده‌ی فایل دیتابیس یا کپی‌کردنش به دستگاه دیگه محافظت می‌کنه؛ در برابر یک هکر که کامل به همون session سیستم‌عامل کاربر دسترسی داره (و می‌تونه از credential store هم بخونه)، محافظت کامل نمی‌کنه — این محدودیتیه که تقریباً همه‌ی اپ‌های دسکتاپ مصرفی دارن.
- SyncEngine فعلاً retry/backoff پیشرفته نداره — اگه push یه رکورد fail بشه، بقیه‌ی صف تا تلاش بعدی صبر می‌کنن (مستندشده در کد، نه پنهان).
